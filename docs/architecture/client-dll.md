# Client DLLs (`modules/client-hook/`)

The client imports `VERSION.dll` (`GetFileVersionInfoW`, `GetFileVersionInfoSizeW`, `VerQueryValueW`). The client side is two DLLs in one Cargo workspace (`modules/client-hook/Cargo.toml`, the Poe2ClientHook submodule, separate from the server workspace):

| Crate | Built as | Deployed as | Role |
|---|---|---|---|
| `poe-hook` | `poe_hook.dll` | `GameFiles/version.dll` | **Loader**, never unloaded: version.dll proxy, log sink, network guard and read-only latch, Vulkan and window hooks, loads and hot-reloads the core. Under Proton it needs `WINEDLLOVERRIDES=version=n,b`. |
| `poe-hook-core` | `poe_hook_core.dll` | `GameFiles/poe_hook_core.dll` | **Debug core**, hot-reloadable: every feature and the overlay. |
| `poe-hook-shared` | (library) | | Config (`poe-hook.toml`), the loader-core C ABI (`abi.rs`), guarded memory reads, module helpers, `trust.rs` (`is_trusted`), `login.rs` (byte logic of the login patch), `sigs.rs` (the signature table in a running process), `offsets.rs` (resolved struct offsets), `redact.rs` (which captured messages carry secrets). Host-buildable: `cargo test -p poe-hook-shared` in the submodule. |
| `poe-hook-mod-api` | (library) | | The **mod ABI**: `HookApi` and the export names of a mod DLL, no dependencies. See [Mod loader](#mod-loader). |
| `poe-hook-mods` | (library) | | Host-buildable mod loader logic: `mod.toml` and `state.toml` parsing, the load plan, the ABI check, the official-mode refusal. `examples/sample-mod` is a tiny mod DLL (`sample_mod.dll`). |
| `poe-hook-sig` | (library) | | The **signature table** matcher: pattern parser, PE reader, scanner, resolver, per-feature status. Pure Rust without Windows dependencies, so `cargo xtask check-build` can use it on the exe file. `signatures/<version>.toml` is embedded by `include_str!`. See [Signature table](#signature-table-signaturesversiontoml). |

## Distribution

A tag `hook-v<version>` in Poe2ClientHook runs `.github/workflows/release.yml`, which builds both DLLs for `x86_64-pc-windows-msvc` and publishes `poe-hook-v<version>-game-<game versions>-windows-x86_64.zip` with a `.sha256`, `SHA256SUMS` and an inner `release.json` (hook version, game versions = the signature tables shipped, mod ABI, SHA-256 of every file): [../guides/releasing-hook.md](../guides/releasing-hook.md). The launcher (`modules/launcher/src-tauri/src/hook.rs`, `hook_ops.rs`) downloads the newest stable release that supports the selected game version, checks the archive and every file, keeps it in `<data>/hook/packages/<version>/` and deploys from there; its *Hook DLL directory* setting overrides it for developers' own builds ([../guides/launcher.md](../guides/launcher.md#client-hook)). `cargo xtask build-dll` and `deploy-client` use the local build.

## Loader (`modules/client-hook/poe-hook`)
| File | Role |
|---|---|
| `lib.rs` | `DllMain`. Loads the config, creates the session folder `logs/poe-hook/<date_time>_<pid>/`, opens the logs and installs the network guard synchronously (the client's crash-report helper connects out within milliseconds), applies the standalone-login patch (`login_patch.rs`), then starts a thread that hooks Vulkan and loads the core. |
| `guard.rs` | Hooks every Winsock connect API ([below](#network-guard-connect-apis)): refuses untrusted connections in private mode (`block_external`), records every connection for the core, and sets the **read-only latch** (official mode, or the first untrusted ("external") connection). Trusted = loopback or `trusted_servers` ([below](#login-mode-and-trusted-servers)). |
| `mods.rs` | The **mod loader** ([below](#mod-loader)): maps the enabled mods' DLLs and calls `poe_mod_init`. Nothing in official mode. |
| `login_patch.rs` | `login_mode = "standalone"`: patches `ClientPlatform_Detect` so the client shows the account-name/password screen ([below](#login-mode-and-trusted-servers)). |
| `vulkan.rs` | Redirects `vkGetInstanceProcAddr`/`vkGetDeviceProcAddr` in `vulkan-1.dll`'s **export table** (jump stubs near the module; under Wine both exports forward to `winevulkan`). Inline hooks there hung the game: Wine's exports are tiny thunks. The game (`0x1410264d0`) resolves everything through them, so it gets our wrappers for instance/device/queue/surface/swapchain creation and `vkQueuePresentKHR`. The swapchain gets `COLOR_ATTACHMENT` and `TRANSFER_SRC` usage added when the surface supports them. |
| `core.rs` | Loads `poe_hook_core.dll` from a temp copy (so the file can be replaced while the game runs) and reloads it when the file changes (`[reload] auto`) or the core asks (overlay button). Unload: the core's `stop`, then a write lock that waits for loader-to-core calls in flight, then `FreeLibrary`. |

## Core (`modules/client-hook/poe-hook-core`)
- `poe_core_start(&HostApi) -> *const CoreApi` is its only export (`poe-hook-shared/src/abi.rs`; `ABI_VERSION` must match).

## Overlay (`[overlay]`)
Dear ImGui 1.92 through [dear-imgui-rs](https://github.com/Latias94/dear-imgui-rs) 0.20 (`dear-imgui-ash` Vulkan backend, `dear-implot` for graphs), drawn by the core inside the game's `vkQueuePresentKHR` on one overlay thread (it owns the imgui context and all overlay Vulkan objects; the game presents from several threads). `overlay/gpu.rs` loads (does not clear) the swapchain image with 3 frame slots; `overlay/input.rs` keeps mouse and keyboard messages, including `WM_INPUT`, from the game while imgui wants them (button releases always pass). `toggle_key` (default Insert) shows/hides it, `snapshot_key` (default Home) saves a snapshot; hidden, only the `OFFICIAL: read-only` badge and notices draw. `scale` multiplies the font; the layout persists in `logs/poe-hook/imgui.ini`. Release builds abort on panic after the core's panic hook logs it. **Ctrl+P** opens a command palette: jump to a page, or type a server command line (`transfer G1_6 random natural natural`); a command needing arguments opens its form on the Commands page.
- Layout: one window with a sidebar of folding groups and entries; an entry with several pages shows them as tabs and reopens on the last one: **PLAY** (Status; Game: Player, Stats, Actions, Entities, Watches; Minimap), **SERVER** (Instances; Commands; Sync: Sync state, Desync), **LOGS** (Live logs: Log, Game log), **RESEARCH**, folded by default (Network: Packets, Protocol, Coverage, Notes, Timing; RE tools: Scanner, Hooks), **SETTINGS** (Features). A page search box lists matching pages, and the last page is remembered (`logs/poe-hook/overlay_page.txt`). The SERVER group is hidden while the read-only latch is on. The look follows the launcher and web admin (`ui/theme.rs`: their colour tokens as ImGui style colours; Cinzel headings, SIL OFL, `poe-hook-core/assets/Cinzel.ttf`).
- Pages:
  - **Packets**: captured messages (filters, decoded view, hex, copy). It can hide identified opcodes so new ones stand out: "Hide this opcode" on a selected message, or the "opcodes" list (every opcode seen this session with count and visibility checkbox; "Hide all named", "Hide all listed" for the current filter, "Show all"); "show hidden" shows them anyway. Saved in `logs/poe-hook/hidden_opcodes.tsv` (`channel, dir, opcode`, kept across sessions). Only the view is filtered: packet files get every message.
  - **Entities**: entities created in the area (initial-state reader), type path from the object-type lookup just before, live grid position (Positioned found by its reader `0x141dd89a0`). After a reload the player is adopted from its frame tick (type unknown). It also lists the selected entity's components with names (Positioned, Stats, Pathfinding, Buffs, Life, Animated, Player, PlayerClass, Inventories, Actor, Render, Targetable, BuffOrbs for the player), addresses and vtables; "scan" opens one in the Scanner. Names come from the entity type's component lookup (`entity+8` → `+0x28`: sorted `{char* name, i32 index}` array from `+0x28` to `+0x30`, as used by get-component-by-name functions such as `0x140150cb0`). The client has no RTTI (the slot before a vtable is a function pointer).
  - **Commands** and **Instances** (our server only): the server's command registry as forms, and its instances with join/close and a new-instance form: [../guides/server-admin.md](../guides/server-admin.md#overlay-pages-our-server-only-server-group).
  - **Notes** page and the Packets editors save opcode and message notes to `logs/poe-hook/packet_notes.tsv` (`kind, channel, dir, opcode, name, session, seq, unix_ms, note, hex`, kept across sessions). **Check this file when working on a message's layout or meaning.**
  - **Minimap**: the client's four cell grids around the player (terrain object found by vtable in the game world; tiles `+0x18`/`+0x20`, 23 cells per tile, 4 bits per cell at `+0xd0`, `+0xe8`, `+0x100`, `+0x118`), shaded by value, with the player and its facing, and the server's position (blue ring, our server). "Export area" writes `terrain_layout_*.tsv` / `terrain_grid_*.bin` on demand (also on official servers, where the automatic export is off).
  - **Stats**: the player's stats by name (`poe-hook-data/stats.tsv`), all stat sets, values changed in the last 3 s highlighted. Stats component (found by name) `+0x1c8` = set 0 (the entity's own stats), other sets in the 16-byte list `+0x1e8..+0x1f0` (container `+0xd8` = set id); a container is a sorted `(i32 key, i32 value)` array at `+0xf8..+0x100` (setter `0x1426acb60`, StatsUpdate handler `0x1421820a0`).
  - **Actions**: starts and ends of the player's Actor actions (`+0x238`, `+0x240`; type at action `+0x120`) with `ActionTypes` names, sampled every simulation frame; also logged ("action start slot 0: DodgeRoll ...").
  - **Protocol**: per opcode, what the field tracer learned: the client functions that read/wrote it (deserializer or serializer first), field layouts (offset:size) and, per field over the last 200 samples, constant / range / plausible f32 / text. "Export now" writes `protocol.tsv` and `ghidra_labels.tsv`.

## Packet capture (`[packets]`, `packets.rs`)
Plaintext of every login and instance message, read inside the client (no cipher is broken, so it works the same on official servers):
- **Received:** the message reader `0x1421c5b90(registry, stream)` (Retn hook). It reads the opcode from the stream's receive ring (decrypted on arrival; ring `+0x298..+0x2a0`, read offset `+0x268`), the registered handlers deserialize the body, and the read offset advances by exactly the message size: the bytes between are the message. Return value low byte 1 = a whole message was read (0 = not enough data yet). Registry byte 0 set = 1-byte opcodes. The caller gives the channel (`0x1420e6d40` login, `0x142120cf0` instance).
- **Sent:** a JmpBack hook at `0x142198187` inside the stream flush `0x142198110`, after its lock and before the cipher (`stream+0x1b8`, slot 1) encrypts in place: pending plaintext `[+0x280] + [+0x260 .. +0x258]`, rbx = stream. Boundaries come from the game-session send `0x14211fa00` (stream `session+0x20f8`, opcode `packet+8`), which records where each message starts and ends in the send buffer. Bytes sent outside it (frame reports, login messages) are split with the fixed sizes from `instance.toml` `[client_body_sizes]` and the `poe-proto` decoders, and marked "unframed".
- Streams without a reply yet are classified by their socket (`stream+0`) and the connection's port: ports in `gateway_list.txt` are login, everything else instance.
- The game has its own plaintext taps (receive `stream+0x150`, send `stream+0x190`, called with `(tap, &ptr, &len)`), probably for packet recording; they are unused here (setting them would be a write).
- Output: the Packets page (`[packets] keep` messages; restored from `packets.jsonl` after a core reload), `packets.jsonl` (one JSON object per message: seq, t, dir, chan, op, name, len, framed, redacted, official, hex) and `packets.txt` in the session folder. Names come from `modules/protocol/opcodes/0.5.5e.hotfix1/*.toml` (embedded at build time), decoded fields from `poe_proto::describe`.
- `redact` (default on) drops the bodies of Authenticate, ResumeSession, AuthenticationResult, InstanceDetails, Hello and client `0x000e` (instance ticket) before anything is stored.

### Field tracer (`protocol.rs`)
While a message is decoded (inside the reader hook) or encoded (inside the session send), the stream primitives are hooked: `0x142197e80` read `(stream, dst, len)` at message offset `stream+0x278`, `0x142197fb0` write `(stream, src, len)` at `+0x258` minus the message start. Each record is (offset, size, return address). The function containing the return address (from `.pdata`) is the deserializer/serializer; functions used by more than two opcodes are generic helpers (strings, chars) and are not chosen. Fields are in `packets.jsonl` (`"fields":"offset:size:caller ..."`) and restored after a reload. Messages sent outside the session (frame reports, login) are not traced. `ghidra_labels.tsv` suggests names like `Read_S2C_instance_00df_AddInventory` only for functions that serve exactly one opcode.

## Debug link with our server (`devlink.rs`)
The DLL's position-report UDP socket also receives sealed `Kind::Debug` frames from the instance server (`key\tvalue` lines; `ack\t<command>\t<result>` for commands, shown as notices) and sends sealed `Kind::Command` frames (the command text). Frames carry the session id, a counter and an HMAC tag made with keys derived from the session's ticket keys ([../protocol/side-channel.md](../protocol/side-channel.md)); the receiver drops anything that does not verify. Server side: `[dev] debug_link` (default on in the code and the example config; off in the committed `modules/server/config/server.toml`, on in the developer config); `sync.rs` remembers each session's UDP address (the source of its latest authentic datagram) and queues its commands, the session tick applies them (`dev_command`) and sends `Player::debug_state`. Works for remote clients. Never while read-only, never to an untrusted address. `scripts/re/send_dev.py` writes a `cmd:<command>` entry to `poe-hook.keys` and the DLL sends it.

## Modes and the read-only latch
`mode` in `poe-hook.toml` (set by `cargo xtask deploy-client [--official]`):
- `private` (default): our server. Crypto bypass on, untrusted ("external") connections refused.
- `official`: official servers, **read-only**. The latch is on from the start: no crypto bypass (the real handshake runs), no position sync, no test input or window-title hooks, no memory writes, no login patch. External connections are allowed. The DLL only observes and logs.
- No mod loads in `official` mode, or when the latch is already on at start ([Mod loader](#mod-loader)).
- In either mode the latch switches on by itself at the first untrusted connection that goes through, and features that act (crypto bypass, position sync) check it again when they act.

## Mod loader
Mods are folders `poe-hook-mods/<id>/` next to the exe (`mod.toml`, an optional entry DLL, data) and `poe-hook-mods/state.toml` (`enabled = [...]`, the load order), the layout the launcher writes ([../guides/launcher.md](../guides/launcher.md#mods)); `cargo xtask deploy-mod` installs one into `GameFiles/` the same way ([../guides/modding.md](../guides/modding.md)). Before the core starts (it hooks function starts, which a later resolution would no longer match) the loader thread resolves the signature table for the mods (only when `state.toml` exists, ~0.3 s); after the core is up it plans the load (`poe-hook-mods`: valid manifest, folder name = id, ABI check, DLL present), then for each mod in order checks dependencies and conflicts against the mods that really loaded, maps the DLL (`LoadLibraryExW`) and calls `poe_mod_init(&HookApi)`. `HookApi` (ABI version 1, `poe-hook-mod-api`): the mod's id and folders, the game version/revision and whether the build is the verified one, `log` (tagged `mod:<id>`), `read_only`, `sig_addr`, `feature_ok`, `field`.
- **Read-only guarantee.** In official mode (and when the latch is already on) the loader loads no mod and does not even read `poe-hook-mods/`; it logs `mods: official mode is read-only: no mod is loaded`. If the latch comes on later (an untrusted connection), loaded mods see it through `read_only()`; they cannot be unloaded.
- **Report to a private server.** The loader records every mod that loaded (id, version, SHA-256 of `mod.toml` and of the entry DLL) and hands the encoded list to the core through `HostApi::mod_report` (core ABI 3; `-1` until the loader is done); the core sends it over the side channel ([Side channel](#side-channel)). Server check: [mod-host.md](mod-host.md#the-login-check-of-the-clients-mods).

## Signature table (`signatures/<version>.toml`)
The DLLs hold **no** game addresses and no game struct offsets in code. Every hook address, patch site and struct offset the DLL reads comes from the signature table of the running build (`modules/client-hook/signatures/0.5.5e.hotfix1.toml`; `poe-hook-sig/src/embedded.rs` `TABLES` picks the one whose PE timestamp and image size match), resolved once when a DLL loads. The matcher is `poe-hook-sig`; the process glue is `poe-hook-shared/src/sigs.rs` (the core uses it through `poe-hook-core/src/sigs.rs`: `gate`, `addr`, `off`).

**Why embedded.** The tables are compiled into both DLLs (`include_str!`), not read from disk: the table must match the code it was built with, a file next to the exe could be stale or edited to point a hook at the wrong bytes, and the launcher deploys the DLL and its table together anyway. The build is chosen by the image's PE timestamp and `SizeOfImage`; the ASCII build revision (`323943`, a string in `.rdata` next to `%S.poecap`, also printed in `Client.txt`) is a third check. Any difference makes the result **unverified** (logged; below). The generator bootstraps a table for a new build: [../re/update-compatibility.md](../re/update-compatibility.md).

**Entries** (85 signatures, 51 fields in 0.5.5e Hotfix 1: 74 `function`, 3 `site`, 8 `ref`):

| Kind | Resolves to | Rule |
|---|---|---|
| `function` (default) | the match start plus `offset` | `pattern` (wildcards `??`, captures `<name:N>`, `<name:rip4+K>`) matches **exactly once** in the code sections; optional `pdata = true` (must be a `.pdata` function start) |
| `site` | an address inside the function of `anchor` | found by `pattern` inside the anchor function (exactly once) or `anchor_offset`; `expect` bytes required; the site must be an **instruction boundary** (linear decode from the function start) |
| `ref` | the target of a RIP-relative operand (call target, global, vtable) | `pattern` with a `rip4` capture, searched in the anchor function (or image-wide) exactly once; used for the three clone-like functions (`object_type_lookup`, `entity_get_render`, `terrain_sample`), found through a unique caller, and for globals |
| `[[field]]` | a struct offset | `pattern` inside the `anchor` function with an integer capture over a displacement; optional `min`/`max`/`align`; `agrees_with` names a second field that reads the same member (both fail on a mismatch); `value` is the table build's value (a different resolved value is logged as `changed`, not an error) |

Common fields: `features` (the DLL features that are **off** when the entry does not resolve), `ghidra` (the table build's address: logging and sanity, never used), `expect` (bytes, wildcards allowed, that must be at the resolved address; for a patch exactly the bytes replaced), `patch` (bytes written, only after `expect` matched), `note`. Patterns wildcard everything a rebuild moves (call and jump targets, RIP-relative displacements, stack-frame sizes and offsets) and keep struct displacements and opcodes.

**Resolution rules.**
1. Resolved once per DLL load in one pass over the code sections (about 0.2 s). The loader resolves only `login_patch`, `login_cache`, `patcher_skip` (before patching, so patched bytes never meet a pattern); the core resolves the rest.
2. A signature with 0 or more than 1 matches, a failed anchor, wrong bytes at the address, a site that is not an instruction boundary, a field outside its limits, or disagreeing partners **fails**: every feature that lists it is **off** and the log says which entry and why (`signatures: feature X: OFF (sig Y: matched 0 times)`). Other features continue. Nothing is hooked or patched on a guess, and there is no fallback to the table build's address. A feature's hooks are all resolved before `hooks::install` runs; the research hooks on by default (`dump_object_types`, `area_export`, packet capture) fail closed the same way. Checked in game with one pattern byte of `read_initial_state` broken: `dump_object_types`, `area_export` and `position_sync` went `OFF`, every other feature stayed `ok`, and the client entered the world without crashing.
3. **Unverified build** (timestamp, size or revision differ, or no table matches): the newest table is tried as a candidate, results are logged `NOT verified`, and with the read-only latch on only the pure observers start (`packets` without the field tracer, `crash_log`, `exit_trace`). In private mode the features that resolved start. The packet capture then redacts **every** login message (`poe-hook-shared/src/redact.rs`, by message name, including `Credentials` `0x0003`), so a renumbered opcode cannot write credentials to `packets.jsonl`.
4. One log block at start: `signatures resolved in N ms`, the build check line, one line per feature (`ok (N entries)` or `OFF (...)`), and a line for every entry that moved or changed value.

**Features in the table:** `login_patch`, `login_cache`, `patcher_skip` (loader); `crypto_bypass`, `side_channel`, `packets`, `dump_object_types`, `area_export`, `generator_trace`, `position_sync`, `entity_probe`, `entity_trace`, `inspect`, `auto_keys_focus` (core). `position_sync` also needs `dump_object_types` (its tick hook). `inspect` (player inspector, stats, entity component names, movement-log fields) and `entity_probe` (the 5-second probe after the player spawned, which calls four game functions directly) are research features: when off, the reads/calls are skipped.

**Struct offsets in the table** (`poe-hook-shared/src/offsets.rs`, unit-tested against the table): entity, type/lookup, component, Positioned, Actor, world and area, generator, terrain, network stream, session and crypto session fields. **Still literal in the code:** the four terrain cell-grid vectors (`+0xd0/+0xe8/+0x100/+0x118`; the export checks each vector's size and writes nothing on a mismatch), the tile record (`0x38` record, fields `+0x30..+0x37`; the export recomputes the client's tile hash and flags a mismatch), the object-type table entry (`0x30`, path at `+8`), area `hash16` (`+0x2a`), world `+0x4b0/+0x4b4`, the packet object's opcode (`+8`), the stream socket (`+0`), component indices Positioned `0` and Actor `9`, Stats containers (`inspect.rs`), the generator-trace object layouts (research) and diagnostic reads of the movement log and entity probe (Render `+0x39a`, action flags `+0x144`, Actor `+0x220..+0x250`, `+0x2a0/+0x2a1/+0x915/+0x916`, Positioned `+0x46c..+0x49c`, world `+0x11c/+0x84a`, vtable slots `0x178/0x200/0x60/0x1f0`).

**`check-build` and the version file.** `cargo xtask check-build <exe>` resolves this table against an exe with `poe-hook-sig`, reports every entry as found, ambiguous or missing with its new address and the delta from `ghidra`, and exits 2 when an entry of a feature listed in the version file's `[client_hook] required_features` fails (1 for research features). The table's `[build]` must agree with the version file's `[exe]`/`build_revision`. New build: [../guides/new-game-version.md](../guides/new-game-version.md).

## Login mode and trusted servers
Two top-level keys of `poe-hook.toml`, written by `deploy-client`:

| Key | Values | Effect |
|---|---|---|
| `login_mode` | `"standalone"` (default in private mode), `"steam"` | `standalone`: the loader patches `ClientPlatform_Detect` (Ghidra `0x142197010`, `40 55 53` → `31 C0 C3`, `xor eax,eax; ret`) in `DllMain`, before the client's first platform query. The client then shows `LoginScreen.ui` (account name, password, Remember Me), sends `0x0003` instead of the Steam ticket `0x0005` and does not initialise the Steam API. Evidence and the packet: [../re/standalone-login.md](../re/standalone-login.md). `steam`: no patch. **Forced to `steam` in official mode** (deploy writes it, and the config loader overrides the file). |
| `trusted_servers` | `["ip:port", "ip:*", "ip"]` (IPv4 literals) | Servers treated like loopback. Deploy writes `[network] public_host` with the login and instance ports, resolving names to IPs; a name under an official game domain (`pathofexile.com`, `pathofexile2.com`, `grindinggear.com`) is refused with a warning (`poe_hook_deploy::trusted::OFFICIAL_DOMAINS`). Empty in official mode (also enforced when the DLL reads the file). |

Patch safety (`poe-hook/src/login_patch.rs`): applied only for `standalone` and only while the latch is off; the function is found by a signature that must match exactly once (`client_platform_detect`) and its first bytes are verified against the table's `expect` bytes (at resolution and right before the write); on a mismatch or missing signature (another build) the patch is skipped with a logged error and the Steam login stays. If the platform cache guard (`platform_cache_guard`, `0x144717144`) is set, the cached value (`platform_cache_value`, `0x144717148`) is reset to 0. The patcher skip (`standalone_patcher_run`) works the same way. Byte logic: `poe-hook-shared/src/login.rs` (unit-tested).

**One trust decision**, `poe_hook_shared::trust::is_trusted(addr)`: loopback (`127.0.0.0/8`, `::1`) is always trusted; otherwise the address must match a `trusted_servers` entry (IPv6 never does). Used by:

| Where | Use |
|---|---|
| `guard.rs` | `external = !is_trusted`. |
| `abi.rs` `Connection.external` | the same flag, recorded for the core (Status page, position sync target). |
| `crypto_bypass.rs` | the bypass runs unless the latch is on or a recorded connection is untrusted. |
| `ui/mod.rs` `custom_server()` | overlay features that talk to our server need the latch off and every connection trusted. |

| Server | `block_external` (private) | Read-only latch | Crypto bypass | Position sync / overlay server pages |
|---|---|---|---|---|
| Loopback | allowed | no | yes | yes |
| In `trusted_servers` | allowed | no | yes | yes (reports go to the trusted address) |
| Anything else (official) | refused; allowed if `block_external = false` or in official mode | **yes**, permanently for the process | no (real handshake) | no |

### The "Create account" button (`register_link.rs`)

The login screen's *Create account* button opens `https://<official host>/account/create?theme=poe2` (the path is a UTF-16 string in `.rdata`) with `ShellExecuteW`, which the client imports from shell32. With `register_url` set in `poe-hook.toml` (the launcher writes the selected server's `<address>/#/register` at Play; `cargo xtask deploy-client` writes the dev server's), the loader hooks that export in `DllMain` (no game address or signature) and opens the private server's register page instead. Only URLs with `/account/create` are swapped, never while the latch is on, and official mode empties `register_url` (deploy and config both). Decision: `poe_hook_shared::register_link::redirect` (unit-tested).

### Network guard: connect APIs
The game uses **only `connect`** (5 call sites; static imports of `PathOfExileSteam.exe`; no `WSAConnect`, `ConnectEx` GUID, `mswsock`/`WinHTTP`/`WinINet` or `WSAConnectByName`/`List`; [../re/network-apis.md](../re/network-apis.md)). The guard still covers every way to open a TCP connection:
- `connect`, `WSAConnect`, `WSAConnectByNameW/A`, `WSAConnectByList` are inline-hooked in `ws2_32` (the last three optional: Wine/Proton does not export `WSAConnectByList`; `connect` and `WSAConnect` are required).
- `WSAIoctl` is hooked: when `SIO_GET_EXTENSION_FUNCTION_POINTER` with `WSAID_CONNECTEX` succeeds, the returned function is inline-hooked too (log `network guard: ConnectEx at ... hooked`); if that fails the ioctl fails (`WSAEOPNOTSUPP`) so the game cannot reach an unguarded `ConnectEx` (with the latch already on the pointer is left alone).
- One rule (`poe_hook_shared::netguard`, unit-tested): trusted (loopback, `trusted_servers`) is allowed and never latches; external is refused in private mode with `block_external` and otherwise latches. Names are never resolved (loader context), so `WSAConnectByName` is trusted only for a numeric IPv4 address and decimal port that are trusted, `WSAConnectByList` only when every entry is. Refused calls fail with `WSAECONNREFUSED`. Log lines: `connect #n ... api=<name>` / `blocked <name> ...`, and at start `network guard: official=... block_external=... latch_at_start=... hooks=...`.
- Not covered: sockets opened by raw system calls (`NtDeviceIoControlFile`/AFD) or code bypassing ws2_32. No send/receive fail-closed rule exists (only the optional `net_trace` hooks `send`/`recv`, and it cannot set the latch).

A client with `login_mode = "standalone"` must not be pointed at an official server (the official login rejects `0x0003`); the latch still protects it. Auto-login needs no DLL code: [../guides/setup.md](../guides/setup.md#remember-me-token-auto-login).

## Building and deploying
Deploying also writes the DLL's name tables to `GameFiles/poe-hook-data/`: `stats.tsv` (network key = `Stats.dat` row + 1, id), `action_types.tsv` and `areas.tsv` (the Instances page's area picker). Symbols for crash reports and the Protocol page come from `assets/symbols.tsv` (`scripts/re/export_symbols.py`, regenerate after documenting addresses; function bounds from `.pdata`). A mod that fails to load is logged (`mods: skipped <id>: <why>`) and skipped, never a crash; `[data]` overlays, `poe_mod_shutdown` and unloading are not implemented. The loader proxies the 16 version.dll exports lazily (`proxy.rs`), buffers logs (`logsink.rs`: `poe-hook.log` next to the exe, the session folder's copy and a 50 000-record ring for the Log tab) and subclasses the game window (`window.rs`).

**Read-only means read-only for the game's state, not the process:** the observers still patch game code in memory (inline detours, a Vulkan hook, the `version.dll` proxy), the DLL can be detected and is against the game's terms; some account risk remains ([../re/crypto.md](../re/crypto.md#other-crypto-in-the-binary), [../guides/official-mode.md](../guides/official-mode.md)).

Commands: [../guides/setup.md](../guides/setup.md).
- Hooks use `ilhook` (pure Rust, iced-x86), because `retour`'s libudis86 C dependency does not build under clang-cl.
- The deploy logic is the `poe-hook-deploy` crate in the same submodule (gateway list, `poe-hook.toml` edits, `steam_appid.txt`, DLL install and backup, Proton launch, crash-dump moving); xtask passes the repo paths (GameFiles, `dumps/<version>`, the Proton prefix) and exports the DLL name tables.
- The opcode tables the Packets page uses are compiled in from Poe2Protocol (`poe_proto::opcodes::v0_5_5e`); `modules/client-hook/protocol` is the nested checkout.
- Mod manifest, ABI and loader rules: `modules/client-hook/docs/mod-manifest.md` (summary: [Mod loader](#mod-loader)).

## Entity tracing (`dump_object_types`)
Besides dumping the object-type table, this feature hooks `0x141e712a0` (entity initial-state reader): it logs each entity's components (vtable, reader, owner) and wraps each serialized component's reader to log the blob span it consumed, which is how [../protocol/entities.md](../protocol/entities.md) was measured (send an all-zero blob, padded, read the spans). Five seconds after the local player entity is created it logs entity flags `+0x8c/+0x8d`, Positioned scales and positions, the world's frame-mode and pause flags, the Render disabled flag (`+0x39a`), a NaN/inf scan of every component and the Animated AO. It also hooks the frame drain (`0x142130840`, dt and caller), the frame-mode entity update (`0x141e7d970`, the player's dt in xmm1), the front-end world update (`0x14167ebc0`, dt) and the initial-state reader (stack references). `POE_HOOK_FORCE_SHOW=1` re-applies the player's render visibility (`0x1416a9990`) as an experiment. It also logs, once per opcode, the caller of the game-session send (`0x14211fa00`, packet +8 = opcode) and the caller of the raw stream writer (`0x142197fb0`) the first time `00 1c` is written, plus the HNC cipher object (stream +0xd0): how the frame report and the HNC channel were found.

### Output folder (`dump_dir`)
`dump_dir` (top level of `poe-hook.toml`) is where the DLL writes datamined and generated files; `cargo xtask deploy-client` sets it to `<repo>/dumps/<version>` as a Windows path (`Z:\` is `/` under Wine) and creates it. Unset, the old locations apply. What lands where: [../../dumps/README.md](../../dumps/README.md).

### Layout export format
`terrain_layout_<tile hash>.tsv` (`terrain/layouts/`): a `size<TAB>w<TAB>h` line, then `x<TAB>y<TAB>tile path<TAB>sub` per sub-tile (23×23 cells).

`sub` is the sub-tile's index in its tile's own orientation, row-major. It comes from the tile record's +0 pointer, which points into the tile object's sub-tile array (0x38 bytes per entry); the lowest such pointer per tile object is the array start. From `sub` and the map position, the server recovers how the tile was rotated or mirrored (`instance-server::spawn::PlacedTile`).

`dump_object_types` also logs, once per opcode, the caller of the game-session send (`0x14211fa00`, packet +8 = opcode). It logs the caller of the raw stream writer (`0x142197fb0`) the first time `00 1c` is written, plus the HNC cipher object (stream +0xd0). That is how the frame report and the HNC channel were found.

### Input injection for tests
`poe-hook.keys` lets a test press keys and move the mouse in the client without touching other windows (never while read-only). The game reads WASD through Raw Input, so the DLL hooks `GetRawInputData`, `GetKeyState`, `GetCursorPos` and, for tests, `GetForegroundWindow` (`POE_HOOK_FAKE_FOCUS`). Entries and environment variables: [../guides/setup.md](../guides/setup.md#poe-hookkeys-entries).

### Movement log
With `dump_object_types`, plus `movement_log = true` or `POE_HOOK_MOVEMENT_LOG` (set by `scripts/test-run.sh`), the DLL logs the player's world position at the start of each simulation update (`frame #n dt world step grid`), the Actor's WASD direction (+0x400) when it changes, the player's facing (Positioned +0x44c and the lock bit) when it changes, and every distinct call stack of SetOrientation (`0x141ddc820`) for the player. Off by default (about 30 lines a second while moving). See [../protocol/movement.md](../protocol/movement.md).

With the movement log on, the DLL logs the player's facing (Positioned +0x44c and the lock bit) when it changes, and every distinct call stack of SetOrientation (`0x141ddc820`) for the player.

## Side channel
Code: `side.rs`, `position_sync.rs`, `devlink.rs`. The DLL talks to **our** instance server over an authenticated side channel: position reports, the debug link and the terrain upload. Format, keys, checks: [../protocol/side-channel.md](../protocol/side-channel.md).

- **Keys.** `side.rs` hooks the instance packet-cipher builder (`0x14212ac10`), copies the session's 64-byte key material and derives the session id and two HMAC keys with `poe_hook_shared::sidechannel` (the code the server runs too). It captures only while the latch is off and every connection is trusted, so there is no session on an official server. The log shows `side channel: session <id>`.
- **Gate.** Every send asks `side::allowed(ip, port)` = `poe_hook_shared::trust::side_channel_allowed(read_only, addr)`: never while latched, only to loopback or a `trusted_servers` entry.
- **Position sync.** One sealed `Kind::Report` UDP frame per player simulation frame (flags, frame counter, x, y, the two action types, the cursor's client-area position with the window size), sent to the newest trusted non-external connection to `position_sync_port`; the server listens for UDP on the same port number. The DLL logs "position sync: target ip:port". The connect hook restores `WSAGetLastError` afterwards (the game checks it after a non-blocking `connect`; changing it broke the login). The server reads the reports only for the opt-in drift checker (`[dev] drift_check`, [../protocol/movement.md](../protocol/movement.md#drift-checker)).
- **Terrain upload.** After `export_layout`, `side::upload_terrain` sends the layout and grid from a background thread: an offer of the tile hash first, then the zlib-compressed files over TCP to the instance port. The first client to generate an area uploads it; others get "server has it". Local files are still written. Hosting: [hosting.md](../../modules/server/docs/hosting.md).
- **Mod report.** `side::report_mods` waits for the loader's list of loaded client mods (`host::mod_report`) and the trusted server connection (`position_sync::server_addr`), sends one sealed `Kind::ModReport` frame over TCP to the instance port and logs `mod report to the server: stored`. The server compares it at login ([mod-host.md](mod-host.md#the-login-check-of-the-clients-mods), [../protocol/side-channel.md](../protocol/side-channel.md#mod-report)).
- **Test entries.** `cmd:<server command>` in `poe-hook.keys` sends that command over the debug link (`scripts/re/send_dev.py`).
