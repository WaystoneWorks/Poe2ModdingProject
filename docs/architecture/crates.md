# Crates and servers

`modules/` holds git submodules, each its own Cargo workspace (or npm/Tauri project). The server, `modules/server` (Poe2Server), has its own `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `target/` and CI, and builds alone (`cargo xtask server build` from the hub). It nests Poe2Protocol, Poe2ClientHook and Poe2WebAdmin. The hub's Cargo workspace is `xtask` only, which uses the server's `poe-config`, `poe-data`, `poe-world`, `poe-proto` and the hook's `poe-hook-deploy`, `poe-hook-sig` as path dependencies. Repositories: [../overview.md](../overview.md).

| Crate | Role |
|---|---|
| `modules/server/crates/poe-config` | Typed `modules/server/config/server.toml` (`server.example.toml` lists every key), and `versions`: the parser of `modules/protocol/versions/<version>.toml`, the single definition of a supported client build. `Config::load` attaches the file named by `[game] version` and fills `protocol_dir` from it ([../guides/new-game-version.md](../guides/new-game-version.md)). |
| `modules/protocol/poe-net` | Transport: `StreamCipher` trait (Salsa20 for login and instance streams), big-endian `Reader`/`Writer` with PoE string and varint encodings, hexdump; the buffered TCP `Connection` is behind the `tokio` feature (servers enable it, the client DLL does not). |
| `modules/protocol/poe-proto` | Message definitions; opcodes come from `modules/protocol/opcodes/<version>/{login,instance,hnc}.toml`. `describe` decodes captured messages for the DLL. |
| `modules/server/crates/poe-data` | Game data: `GameFiles` (Bundles2 through `poe_data_tools`, override directories in front) and `GameData::table("WorldAreas")` (`.datc64` decoded with the community schema, columns by name). |
| `modules/server/crates/poe-store` | `Store` trait plus SQLite: accounts, characters, saved positions; owns the schema migrations (`0006` adds passwords, roles and tokens). |
| `modules/server/crates/poe-accounts` | `AccountStore` trait and SQLite implementation: usernames, argon2id passwords (over the client's SHA-256(UTF-16LE) digest), roles, revocable per-cluster tokens, the `account` command. |
| `modules/server/crates/poe-mod-host` | Server mod host: `mods/` folder, load plan, native libraries, data-tier commands, events, submitted commands, client-mod advertisement, login comparison. [mod-host.md](mod-host.md) |
| `modules/server/crates/poe-cluster` | Coordination: tickets (`TicketRegistry`), login sessions (logout, transfers), `InstanceDirectory`, `AdminControl` (what the web API needs from the instance server), `ModDirectory` (offered client mods, implemented by the mod host). In-process now; traits allow a split deployment. |
| `modules/server/crates/poe-web-api` | HTTP/WebSocket API (axum): register, login, tokens, admin endpoints running the command registry through `poe_cluster::AdminControl`, live log layer, OpenAPI, static web admin. [web-api.md](web-api.md) |
| `modules/server/crates/poe-world` | Terrain generation (the client's generator, ported; [../status/terrain.md](../status/terrain.md)). |
| `modules/server/crates/poe-game` | Simulation: instance `World` (entities, frame clock), `GridSource` terrain grids (client dump `Grid`, `VecGrid`), the movement seam (`MoveInput`, `MoveEvent`, `MovementModel`, `Mover`; typed, no opcodes; stub `StandStillModel`; [instance-world.md](instance-world.md#the-movement-seam-movementrs), spec [../protocol/movement.md](../protocol/movement.md)), curve loader `motion_data`, character stats. Reference fixtures under `tests/fixtures/` derived by `scripts/re/movement_fixtures.py` (no test reads them now). |
| `modules/server/servers/login-server` | Login protocol: auth, leagues, characters, hand-off and transfers. |
| `modules/server/servers/instance-server` | Instance protocol: areas, the instance actor (`actor.rs`: one task per instance owns the `World` and serves all its sessions), character blobs (`appearance.rs`), movement glue, chat, server commands (`commands.rs`, `exec.rs`), live sessions. |
| `modules/server/servers/poe-server` | Runs login server, instance server and web API in one process. |
| `xtask` (hub) | `cargo xtask` ([../guides/setup.md](../guides/setup.md)): wrappers over `poe-hook-deploy`, `server` (`server.rs`: build, run with the hub as working directory, web admin rebuild), the terrain matrix (`terrain_matrix.rs`), `check-build` (`check_build.rs`, `fingerprint.rs`: scans a game exe with `poe-hook-sig`, compares opcode tables, strings and game data; report `dumps/<version>/check-build.md`), `versions` (`versions.rs`: keeps the launcher's copies of the version files). `openapi` delegates to the server's own `modules/server/xtask`. |
| `modules/web-admin` | Poe2WebAdmin (Svelte 5 + Vite): admin site on the web API, types generated from `modules/server/docs/openapi.json`. [web-api.md](web-api.md#the-web-admin-spa) |
| `modules/launcher` | Poe2Launcher (Tauri 2 + Svelte 5, own workspace in `src-tauri`): server profiles, Steam depot install, deploy and start of the game, mods. [../guides/launcher.md](../guides/launcher.md) |
| `modules/client-hook` | Poe2ClientHook (own workspace): client DLLs (Windows target: loader, debug core, shared config/ABI) and `poe-hook-deploy`, behind `cargo xtask deploy-client`/`revert-client`/`deploy-core`/`run-client`. Nested `protocol/` = Poe2Protocol. |

The server mod ABI (`poe-mod-api`) is in the SDK repository, pinned by git tag.
