# Reverse engineering

How the client is analysed and where the results are written down. The rules (static analysis only, official servers read-only, never the Steam install) are in [../../CLAUDE.md](../../CLAUDE.md).

**Scope of what is committed.** Everything under `docs/re/` is research about the 0.5.5h client: addresses, struct offsets, opcode meanings, formats and function names, in our own words. No decompiler output, game code, assets, bundles or data tables are pasted here or anywhere in the repositories (datamined dumps stay in the git-ignored `dumps/<version>/`). Addresses are for build 0.5.5h only and change with every client update ([update-compatibility.md](update-compatibility.md)). The project is unofficial and not affiliated with Grinding Gear Games ([disclaimer](../../README.md#disclaimer)).

## Reverse engineering access
- **Ghidra MCP** (`mcp__ghidra__*`). Call `connect_instance("Poe2ModdingProject")` first. Work in **`/0.5.5h/PathOfExileSteam.exe`** (image base 0x140000000), the build in `GameFiles/` and the only supported one; it carries all names, signatures, comments and data types of the earlier programs (ported with `scripts/re/ghidra/PortFromAddrMap.java`, [below](#a-new-build-in-the-ghidra-project)). The project may still hold older programs (`/PathOfExileSteam.exe` is 0.5.5e, older build folders are empty; unused, close them to avoid `program=` mix-ups). **Every address in these docs and in code comments is a 0.5.5h address** (older ones were moved with `scripts/re/convert_addrs.py`).
- **`decompile_function` and `get_function_by_address` use the active program and ignore `program=`**: make the 0.5.5h program the active one in the CodeBrowser.
- `run_script_inline` needs `GHIDRA_MCP_ALLOW_SCRIPTS=1` in Ghidra's environment (the user starts it; `GHIDRA_MAXMEM=32G` too). A script running longer than the MCP's 30-minute call limit is aborted on the client side and leaves an aborted transaction behind (the program then cannot be saved: restart Ghidra); run long work in a background thread that saves by itself.
  - Use targeted calls (`search_strings`, `get_xrefs_to`, `decompile_function`).
  - Huge functions (packet factories) give 20k+ token decompiles: use `disassemble_function` on ranges or search by constant.
  - **Rule: every function you read during a task gets renamed and commented in Ghidra right then** (`rename_function_by_address`, `set_plate_comment`; `Module_Action` names as in the docs), and the program is saved (`save_program`) before the task ends. Name only what you understood; a guess goes in the plate comment as `hint:`. Record stable findings in [addresses.md](addresses.md).
  - Searching: skip library code with the tag `lib` (`search_functions_by_tag`), read `str:` hints in plate comments, and treat `Class::vf_XX` as a vtable slot name only ([naming pass](#naming-pass-g1)).
- **x64dbg / dynamic debugging**: not installed. **Ask the user** when it would help (runtime values such as keys, crash triage, verifying a hook).
- The client DLL can log plaintext packets (trace feature): [../architecture/client-dll.md](../architecture/client-dll.md#packet-capture-packets-packetsrs).

### A new build in the Ghidra project
The old program stays; the new exe becomes a second program in the same project (folder `/<version>/`) and the RE work is carried over:
1. Start Ghidra with `GHIDRA_MCP_ALLOW_SCRIPTS=1 GHIDRA_MAXMEM=32G` (the default heap is a quarter of RAM; Version Tracking ran out of it).
2. Import `GameFiles/PathOfExileSteam.exe` into `/<version>/` without analysis (`import_file`, `auto_analyze=false`), then `run_analysis` (about 30 minutes; wait with `analysis_status`), then **save at once** (`save_program`).
3. Run `scripts/re/ghidra/PortFromAddrMap.java` on the new program (`run_ghidra_script` finds a script only in `~/ghidra_scripts` or `<project>/ghidra_scripts`, so copy the script there; the MCP deletes a symlink) with arguments `<addr_map.tsv> <old program path>`, for example `/0.5.5f/PathOfExileSteam.exe` (the map from `scripts/re/addr_map.py`). It copies the data types, name, namespace, signature and plate comment of every named function (functions outside `.pdata` are placed by a neighbour's delta and confirmed by their first bytes) and the comments inside functions; it takes seconds and can be rerun. Hotfix 1 result: 795 data types, 862 named functions right (113 renamed, 2 created), 384 signatures; the 164 left are loader names (`DelayLoad_*`, CRT) that the new program has under its own addresses; comments outside functions were all analysis output (RTTI, imports), made again by the new analysis. Save.
4. Ruled out: Ghidra's Automatic Version Tracking with the default heap (filled 15.5 GB and stalled; a background run failed after 85 minutes with an internal `VTAssociation` error). For a hotfix (functions only moved) the address map is exact and fast; for a bigger update (0.6) use Version Tracking (GUI: *Tools > Version Tracking*, the wand button) with a large heap.
5. Check with `search_functions_enhanced(has_custom_name=true)` on both programs and spot-check signature-table addresses. Afterwards the old game copy (`GameFiles-<old>/`) can go: the old program keeps its own copy of the exe in the project, and `dumps/<old>/exe/` keeps one for `addr_map.py`. Then regenerate the DLL's crash-log symbols: `ExportNamedFunctions.java` with the output path `dumps/<new>/ghidra/ghidra_named_functions_p1.json`, then `scripts/re/export_symbols.py`.

### Naming pass (G1)
A scripted pass over `/0.5.5h/PathOfExileSteam.exe` (2026-11-19). Names come only from reliable sources; weaker evidence is a tag or a plate-comment hint. Scripts in `scripts/re/ghidra/` (copy to `~/ghidra_scripts`, run with `run_ghidra_script`; each takes `<out dir>` and does a dry run unless the last argument is `apply`; reruns are safe); raw output in `runtime/ghidra-naming/`. Before: 115,197 functions, 113,885 `FUN_`.

| Step | Script | Result | `FUN_` after |
|---|---|---|---|
| 1 RTTI | `G1RttiNames.java` | 5,597 complete object locators and vtables (all already labelled `Class::vftable` by Ghidra's RTTI analyzer, which also sizes them); 26,140 slots, 5,433 distinct functions: **4,900 named `Class::vf_XX`** (XX = slot in hex; `vf_XX_oNN` for the vtable of the subobject at offset NN; a function in several vtables is named for the class that is a base of all the others), 23 kept their name, 510 shared by unrelated classes (identical-code folding) left unnamed. The game's own code is built without RTTI: the names are exprtk 4,618, std 203, `Utility` 42, spirv_cross 25, 12 CRT internals (undname nodes, `type_info`, anonymous) | 108,985 |
| 2 Libraries | `G1FidLibs.java`, `G1LibTags.java` | Ghidra's Function ID (VS2012 to 2019 databases) matches 1,212 functions: 758 already named by the import-time FID analyzer (some are false positives, e.g. 101 `MRECmpImpl` and MFC `CWinApp` methods), 454 with several candidate names (a `fid?:` hint), **none with a single name, so no renames** (the client uses a newer MSVC). Tags `lib` plus `lib:<name>` on **6,307 functions**: msvc 1,398 (FID, std and undname namespaces, CRT strings), exprtk 4,753, oodle 69, stb_image 27, spirv_cross 26, libcurl 18 (8.5.0), cryptopp 8, mimalloc 5, zlib 4 (inflate 1.2.8). Found by RTTI namespace or by strings only the library has (table in `G1LibTags.java`). Present but not tagged: Brotli (only its dictionary). Loaded as DLLs, not linked: FMOD, Bink, Steam, EOS, DXC, XeSS | 108,985 |
| 3 Strings | `G1StringHints.java` (input `strings_va.py` output) | 8,736 message strings (debug, error, log texts and `__FILE__` paths, no asset paths); 5,627 texts used by exactly one non-library function: **2,505 functions** get up to three `str: <text>` plate-comment lines and the tag `str` | 108,985 |
| 4 Known names | `scripts/re/known_names.py`, then `G1ImportNames.java` | 417 names from the docs (an upper-case `Module_Action` identifier written right next to the address) and the DLL's `ghidra_labels.tsv` (0.5.5h sessions): **218 functions renamed**, 17 labels (doc-named sites inside functions and addresses Ghidra has no function at), 168 already so; 4 doc names applied over a different DLL label (the DLL name is a `dll label:` plate line); 9 conflicts not applied (below) | 108,769 |

Conflicts left for the docs to settle (not applied): `Action_OnAnimationEvent` on `0x141985520` and `0x141a48fd0`; `Action_ReturnOne` on `0x140108820` and `0x140145100`; `MoveEvent_ClipToWalkable` on `0x141f72180` and `0x141f72260`; `Pathfinding_GetSpeed` on `0x141dda660` and `0x141e5bfc0`; `SprintPart_EndCheck` on `0x14141eb40` and `0x141b85610`; `0x141edeb10` is `Pathfinder_Plan` in [addresses.md](addresses.md) and `Pathfinding_Search` in [movement-coverage.md](movement-coverage.md); `0x141edc480` is `SkillUseParams_Write` in Ghidra and `Write_C2S_instance_01a5_UseSkill` from the DLL; the DLL's `Read_S2C_instance_0355_WarpList` (`0x14217b287`) and `Read_S2C_login_0015_CharacterList` (`0x142728feb`) are addresses inside functions.

## Offline scripts (`scripts/re/`, no Ghidra needed)
Run with the project's Python environment from `third_party/fetch-tools.sh` ([../guides/setup.md](../guides/setup.md#tools)): `third_party/pyenv/bin/python scripts/re/<script>.py <args>`. Addresses are Ghidra virtual addresses in hex; `pe.py` holds the shared PE-reading helpers. Most scripts read `GameFiles/PathOfExileSteam.exe`.

| Script | Use |
|---|---|
| `disasm.py <start_va> <length>` | Disassemble a range |
| `find_disp.py <disp> [min max]`, `find_imm.py <imm> [min max]` | Find instructions using a struct-field displacement or a 32-bit immediate |
| `sig_gen.py <spec> [exe]` | Generates `modules/client-hook/signatures/<version>.toml` from a spec of Ghidra addresses (`sig_spec_0.5.5h.py`): unique wildcarded function prefixes, anchored site/ref patterns, struct-offset captures. Verify with `cargo run --release -p poe-hook-sig --example resolve -- <exe>` in `modules/client-hook` |
| `addr_map.py <old exe> <new exe> [--out tsv] [--map <va>...]` | Old-to-new address map of a rebuilt exe from the two `.pdata` function lists (hotfixes: functions keep their order and move by deltas); `same` rows moved, `gap`/`lost` rows are the changed functions. Input of the hotfix signature spec ([../guides/new-game-version.md](../guides/new-game-version.md)) |
| `convert_addrs.py <old exe> <new exe> <addr_map.tsv> [--skip <file>:<a>-<b>] [--dry-run] <file>...` | Rewrites client addresses in docs and comments from an old build to the new one, in place: code by the map, data through the old code's RIP-relative references (all must agree) or unique bytes; lists what it cannot place |
| `ghidra/PortFromAddrMap.java` (Ghidra script) | Carries names, signatures, comments and data types from an old build's program to a rebuilt one with `addr_map.tsv` ([above](#a-new-build-in-the-ghidra-project)) |
| `ghidra/G1*.java` (Ghidra scripts), `known_names.py [out.tsv]` | The naming pass and its rerun: RTTI slot names, library tags, string hints, names from the docs and the DLL ([above](#naming-pass-g1)); `G1Counts.java` prints the function, `FUN_` and tag counts |
| `bundlediff/` (Rust, `cargo run --release --manifest-path scripts/re/bundlediff/Cargo.toml -- <old game dir> <new game dir>`) | Which virtual files of `Bundles2` a build added, removed or changed (content SHA-256; reads only bundles whose index records moved) |
| `version.py` | (module) The client version the scripts work on: the newest `modules/protocol/versions/<version>.toml`, or `$POE_VERSION` |
| `strings_va.py [out.tsv]`, `refs.py <start> <end>` | Every string outside code with its address; the calls and the data references (with their strings) in a range |
| `find_switches.py <func_start> <length>` | List the jump-table switches in a function and the opcodes each case handles; prints the arguments `dump_factory.py` needs (base, count, dword and byte table RVAs, default case) |
| `case_strings.py <func_start> <len> [window]` | Strings referenced near each switch case |
| `dump_factory.py <base> <count> <table_rva> <default_va> [out.json] [--bytes <byte_table_rva>]` | Dump a packet factory (opcode -> case, size, vtable, deserializer) into `dumps/<version>/ghidra/`; instance factory (`FUN_142180510`): `dump_factory.py d 363 2182c3c 142182c20`; login factory (`0x14215f5d0`, index table): `dump_factory.py 1 47 215f6d8 14215f6bc dumps/0.5.5h/ghidra/login_factory_s2c.json --bytes 215f74c` (`find_switches.py` prints base 0 for this switch, but index 0 is opcode 1); factory 2's first switch has base `0x1ae`. The dumps are the input of the opcode drift baseline (`cargo xtask check-build <exe> --write-fingerprints`, [../guides/new-game-version.md](../guides/new-game-version.md)) |
| `find_opcode_stores.py`, `find_packet_senders.py <vt_lo> <vt_hi>`, `find_stack_packets.py <min> <max> [opcode…]` | Find packet constructors and senders (opcode stored at object +8) |
| `packet_layout.py <opcode...>` | Recover a packet's layout from its serializer and deserializer; the vtable-to-opcode map is in `dumps/0.5.5h/ghidra/packet_classes.json` |
| `export_symbols.py` | Build the DLL's symbol table (`modules/client-hook/poe-hook-core/assets/symbols.tsv`) from Ghidra's named functions (`ghidra_named_functions_p1.json` in `dumps/<version>/ghidra/`, `{"results":[{address,name}]}`, written by an inline Ghidra script after the port; version from `version.py`) and the address tables in [addresses.md](addresses.md); rerun after documenting new addresses |
| `packets_diff.py`, `clientlog_entries.py`, `clientlog_terrain.py` | Compare captures, read the live client log: [captures.md](captures.md) |
| `movement_sequences.py list\|events\|scen\|never <session>` | Movement and skill message sequences in a capture, with frame offsets against `0x2f7` ticks: [../protocol/movement.md](../protocol/movement.md) |
| `tick_timing.py [packets.jsonl ...]` | Official `0x2f7` tick sizes, rate, spacing, `0x2f8` count and stall catch-up: [../protocol/movement.md](../protocol/movement.md#timing) |
| `send_dev.py` | Send a server command over the debug link: [../guides/setup.md](../guides/setup.md#unattended-client-tests) |
